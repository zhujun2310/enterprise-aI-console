# ADR 0003: 业务模块 Mock 数据策略（先闭环后接真接口）

## Status

Accepted

## Context

设备中心与 Dashboard 都需要“可演示、可联动、可迭代”的效果，但真实后端与数据源在早期可能不完备。

如果只用静态 UI 占位，会带来：

- 页面交互不可验证（分页/筛选/状态流转/批量操作无法跑通）
- Store/API 边界难以稳定下来
- 后续接真实接口时容易大改

## Decision

采用“可运行的 Mock 数据层 + 统一 API 入口 + Store 驱动页面”的策略：

- Mock 数据层具备业务最小闭环能力：分页、筛选、排序、状态回写、批量动作
- API 层对外暴露稳定函数签名（例如 `getDeviceList/getDeviceDetail/...`）
- 页面不直接依赖 Mock 数据结构，只依赖 API 与 Store

这样后续切换到真实接口时，只需要替换 API 实现，不重写页面交互。

## Alternatives

### 1) 纯 UI Mock（写死列表/写死状态）

优点：

- 开发快

缺点：

- 交互无法验证
- 后续接真实接口通常需要重构

### 2) 直接对接真实接口（前期强依赖后端）

优点：

- 一步到位

缺点：

- 前期阻塞风险高
- 需求尚未稳定时改动成本大

## Consequences

正面：

- 演示闭环完整，交互可验证
- API/Store 边界提前稳定，利于后续替换真实数据源

代价：

- 需要维护 Mock 数据层与协议
- 必须控制 Mock 复杂度，避免过度工程化
